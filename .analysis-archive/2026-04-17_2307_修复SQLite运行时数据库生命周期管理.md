
<analysis>
context:
  侦察发现以下关键事实：

  1. **运行时数据库生命周期管理现状**：
     - `table-storage-strategy.ts` 维护一个全局单例 `currentProvider`（可能是 `SqlTableService` 或 `NativeTableServiceAdapter`）
     - `SqlTableService` 内部持有 `SqliteEngine` 实例，`SqliteEngine` 持有 sql.js 的内存数据库 `Database` 实例
     - `SqlTableService.dispose()` 会调用 `engine.dispose()`（关闭数据库）+ `disposeGlobalNameMapper()` + 重置 `_initialized = false`

  2. **初始化时机**：
     - 脚本启动时：`mainInitialize_ACU()` → 轮询等待 `chatId` → `initWithChatId()` → `resetScriptStateForNewChat_ACU()` → `loadOrCreateJsonTableFromChatHistory_ACU()`（这是原生模式的加载，不涉及 SQLite）
     - 注意：**启动时没有调用 `initStorageProvider()`**！SQLite Provider 的初始化完全依赖 `CHAT_CHANGED` 事件中 1200ms 延迟后的 `reloadStorageProvider()` 调用
     - `getStorageProvider()` 有懒初始化逻辑：如果 `currentProvider` 为 null，会根据当前模式创建一个新的 Provider（但不调用 `loadFromChat`）

  3. **CHAT_CHANGED 事件处理流程**（init.ts 第 109-203 行）：
     - **同步部分**：`resetScriptStateForNewChat_ACU(chatFileName)` → 重置状态、加载设置、加载聊天消息、调用 `loadOrCreateJsonTableFromChatHistory_ACU()`（原生模式的 JSON 加载）
     - **1200ms 延迟部分**（setTimeout 内）：
       a. 检查聊天是否已切换（防止快速切换导致的竞态）
       b. `if (isSqliteMode())` → `reloadStorageProvider()` → dispose 旧实例 + 创建新 SqlTableService + loadFromChat
       c. `refreshMergedDataAndNotifyWithUI_ACU()` → 刷新 UI

  4. **BUG 1 — 换卡不销毁**：
     - SillyTavern 的 `CHAT_CHANGED` 事件在换卡时也会触发
     - 但 `resetScriptStateForNewChat_ACU()` 不涉及 SQLite 数据库的销毁或重建
     - SQLite 数据库的重建在 1200ms 延迟的 setTimeout 中
     - 在这 1200ms 内，旧卡的 SQLite 数据库实例还活着，getStorageProvider() 返回旧实例
     - resetScriptStateForNewChat_ACU() 中的 loadOrCreateJsonTableFromChatHistory_ACU() 会把 currentJsonTableData_ACU 设为新卡的数据，但 SQLite 引擎里还是旧卡的数据——数据不一致

  5. **BUG 2 — 换聊天不销毁**：
     - 同上，1200ms 延迟窗口内数据不一致

  6. **BUG 3 — 启动时不初始化 SQLite**：
     - initWithChatId() 调用链中没有 initStorageProvider() 或 reloadStorageProvider()
     - 如果用户是 SQLite 模式，脚本启动时 SQLite 引擎不会被初始化

  7. **根本原因**：
     - resetScriptStateForNewChat_ACU() 不知道 SQLite Provider 的存在
     - SQLite 的生命周期管理被分散在 init.ts 的 CHAT_CHANGED 事件回调中（presentation 层）
     - reloadStorageProvider() 被放在 1200ms 延迟中

needs:
  1. 换卡/换聊天时，必须在状态重置的同时（或之前）销毁旧的 SQLite 数据库实例
  2. 脚本启动时，如果是 SQLite 模式，必须初始化 SQLite Provider
  3. 消除 1200ms 延迟窗口内的数据不一致问题
  4. SQLite 生命周期管理应该集中在 service 层

key_challenges:
  1. resetScriptStateForNewChat_ACU() 是同步函数中调用异步操作，而 reloadStorageProvider() 是异步的
  2. 1200ms 延迟是为了等待 SillyTavern 完成 DOM 渲染——不能简单删除，但可以把 SQLite 销毁提前
  3. loadOrCreateJsonTableFromChatHistory_ACU() 和 reloadStorageProvider() 都会设置 currentJsonTableData_ACU
  4. 多处代码通过 getStorageProvider() 获取 Provider

confidence: HIGH

approach:
  核心思路：在 CHAT_CHANGED 事件的同步处理阶段，立即 dispose 旧的 SQLite Provider，然后在 1200ms 延迟后重建。同时在启动流程中加入 SQLite 初始化。

  具体方案：
  1. 在 table-storage-strategy.ts 中新增 disposeStorageProvider() 函数
  2. 在 init.ts 的 CHAT_CHANGED 回调中，resetScriptStateForNewChat_ACU 之前立即 dispose
  3. 在 initWithChatId() 中加入 SQLite 初始化
  4. 新增测试

  三维评分：
  - 可维护性: 5/5 — 新增一个明确职责的 disposeStorageProvider 函数，调用点清晰
  - 健壮性: 5/5 — 消除了 1200ms 窗口内的数据不一致问题
  - 可扩展性: 5/5 — disposeStorageProvider 是通用函数

edge_cases:
  - 快速连续切换聊天：旧的 setTimeout 回调会被 scheduledChatIdentifier 检查拦截
  - CHAT_CHANGED 事件的 chatFileName 无效：resetScriptStateForNewChat_ACU 已有守卫，会直接 return，此时不应 dispose——但 dispose 在 reset 之前执行，需要在 dispose 前也检查 chatFileName 有效性
  - 非 SQLite 模式：disposeStorageProvider 对 NativeTableServiceAdapter 调用 dispose 是安全的
  - getStorageProvider() 在 dispose 后被调用：懒初始化会创建新实例但没有 loadFromChat
  - 启动时 chatId 不可用的轮询场景：轮询成功后调用 initWithChatId，此时应该初始化 SQLite
