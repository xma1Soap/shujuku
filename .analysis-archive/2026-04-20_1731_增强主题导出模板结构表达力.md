<analysis>
context:
  1. 当前导出文件之所以“看起来还是老样子”，并不是单纯因为导出逻辑没生效，而是因为它最终仍然执行 `JSON.stringify(file, null, 2)`，输出的是**标准 JSON**。标准 JSON 天然不会保留源码里的注释、分组标题、中文说明块。所以 `createThemeTemplateBase()` 里那些注释说明，在最终文件里本来就不可能出现。
  2. 当前导出结构仍然只有两层核心内容：
     - 根级：`formatVersion`、`exportedAt`、`theme`
     - 主题内：`variables`、`customCSS`、`windowChromeVariables`、`toastVariables`、`visualizerVariables`、`previewColors`
     这就是用户仍然觉得“还是这个样式”的根本原因——文件结构本身并没有显著变得更像“模板”，只是 `theme` 对象里的字段补齐了。
  3. `theme-registry.ts` 当前的 `createEditableThemeTemplate(theme)` 只是把模板骨架和当前主题 merge 到 `theme` 对象内部，没有新增任何**显式模板说明字段**、**模块导航字段**、**编辑指引字段**。所以从用户视角看，它仍然像一个主题快照，只不过稍微完整了一点。
  4. `importThemeFromFile()` 目前只校验：
     - `raw.formatVersion === 1`
     - `raw.theme.id/name/variables` 存在
     这意味着在导出文件根级新增额外的模板辅助字段（例如 `templateMeta`、`editableModules`、`guide`）是安全的，导入不会被破坏，因为解析逻辑会忽略未知字段。
  5. `theme-types.ts` 当前 `ACUThemeFile` 只有三个字段：
     - `formatVersion`
     - `exportedAt`
     - `theme`
     没有为模板辅助信息保留空间，所以即使现在想导出“更像模板”的结构，也没有类型层的正式表达。
  6. 用户这次的反馈非常关键：他不是在说“字段数量还不够一点点”，而是在说“导出的文件整体形态仍然像旧式主题对象”。这说明问题已经从“补字段”升级成“导出格式表达能力不够”。
  7. 也就是说，真正该修的不是继续往 `theme` 对象里塞零散字段，而是让导出文件增加一层**模板语义化结构**，例如：
     - 这是什么类型的导出
     - 基于哪个当前主题
     - 有哪些可编辑模块
     - 每个模块对应哪些字段
     - 推荐修改入口在哪里
     只有这样，文件一打开才会显著区别于普通主题快照。

needs:
  1. 让导出文件在结构上明显表现为“完整可编辑模板”，而不是仍然像一个普通主题对象快照。
  2. 保持导入兼容：新增的模板辅助字段必须是附加的，不影响现有 `raw.theme` 导入。
  3. 为主题作者提供显式的模块导航和编辑说明，而不是继续指望他们从一大坨 `variables` 中自行猜测。
  4. 保持导出结果既可直接导入，也适合作为二次编辑起点。

key_challenges:
  1. JSON 不能保留注释，所以“模板感”不能再依赖源码注释，必须转化为真实 JSON 字段。
  2. 不能破坏现有导入逻辑；因此新增模板说明必须是非侵入式扩展。
  3. 需要在“结构更丰富”和“文件仍然简洁可用”之间保持平衡，不能把导出结果做成难以阅读的巨大噪音文件。
  4. 模块说明不能只是空洞文字，必须和实际可编辑字段对应起来，否则又会变成一层新的摆设。

confidence: HIGH
  - 侦察信息充分，根因已明确：当前问题是导出格式表达能力不足，而不是单纯某个字段漏导出
  - 现有导入逻辑对未知字段天然宽容，给了我们安全扩展格式的空间

approach:
  采用“保留 `theme` 作为可导入主体 + 在根级新增模板辅助结构”的方案。
  1. 在 `theme-types.ts` 中扩展 `ACUThemeFile`，新增可选字段：
     - `templateMeta`
     - `editableModules`
     - `guide`
     这些字段只用于模板表达和二次编辑导航，不参与运行时主题应用。
  2. 在 `theme-registry.ts` 中新增模板辅助数据构造器：
     - `templateMeta`：说明这是一份“基于当前主题生成的完整可编辑模板”
     - `editableModules`：按模块列出当前主题的可编辑入口，例如 core/colors、controls、confirm、overlay、windowChrome、toast、visualizer、customCSS
     - `guide`：给出简短但真实可用的编辑说明和建议修改顺序
  3. `exportThemeToFile()` 继续导出可直接导入的 `theme`，但同时附带上述模板辅助结构。这样用户打开文件时会明显看到“这是模板”，而不是普通主题快照；同时老导入逻辑仍然只读 `theme`，不会炸。
  4. 不去发明第二套主题格式，不去改变 `raw.theme` 的导入契约。导出增强是附加层，不是替换层。
  
  三维评分：
  - 可维护性: 5/5 — 保留现有 `theme` 主体，模板辅助信息单独挂在根级，职责清晰
  - 健壮性: 5/5 — 不破坏导入兼容，旧解析逻辑仍然成立
  - 可扩展性: 5/5 — 后续新增模块时，只需在 `editableModules` 生成器中追加说明，不必改导入协议

edge_cases:
  - 旧版本导入逻辑若只读取 `theme`，必须完全忽略新增 `templateMeta/editableModules/guide` 字段，不能报错
  - 当前主题某些模块对象为空时，`editableModules` 仍应显示该模块，并标明“当前为空，可自行补充”，否则模板导航会继续显得残缺
  - `customCSS` 为空或只有默认模板内容时，`guide` 应明确提示优先修改哪些变量/模块，而不是只留一个空字符串
  - 导出文件不能因为附加说明过多而变得不可读；模块说明应尽量结构化、短句化
  - 必须避免把模板辅助说明和真实可导入主题字段混淆到一起，防止用户误改说明字段却以为那会影响 UI
