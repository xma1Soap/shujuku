
<analysis>
context:
  1. SQLite 模式（sql-table-service.ts）的 loadFromChat() 方法有两条路径：
     - mergedData 有值（加载历史聊天）：调用 syncBridge.loadFromTableData(mergedData) 立刻建表+灌数据 ✅ 正确
     - mergedData 为 null（新开卡）：只初始化引擎，不建表，注释写着"建表延迟到第一次 applyEdits/executeQuery/executeMutation 时" ✅ 看起来正确
  2. _ensureTablesFromTemplate() 在 applyEdits(L152)、executeQuery(L198)、executeMutation(L213) 三处被调用——这是"延迟建表"的实现。
  3. 问题在于：_ensureTablesFromTemplate 不区分"新开卡首次填表"和"老卡正常运行"。它的逻辑是：解析 TABLE_TEMPLATE_ACU 获取模板中所有表，然后检查 SQLite 中缺失的表并建表。
  4. 冈部说的问题是：新开卡时，用户可能还要改表结构（比如在可视化编辑器中修改 DDL、增删列等），但如果此时有任何 executeQuery 被调用（比如前端查询表数据用于展示），_ensureTablesFromTemplate 就会提前把表建出来。表一旦建了，用户再改表结构就会出问题（SQLite 中已有的表不会被重建）。
  5. JSON 模式（table-service.ts）的 loadOrCreateJsonTableFromChatHistory_ACU 也有类似问题：当 mergedData 为 null 时，它调用 initializeJsonTableInChatHistory_ACU()，这个函数会立刻调用 parseTableTemplateJson_ACU({ stripSeedRows: true }) 并设置到 currentJsonTableData_ACU。但 JSON 模式下"改表"只是改 JSON 对象，不存在 SQLite 那种"表已建无法改结构"的问题，所以 JSON 模式的问题不大。
  6. 核心问题集中在 SQLite 模式：_ensureTablesFromTemplate 在新开卡场景下不应该被 executeQuery 触发。只有 applyEdits（真正填数据）和 executeMutation（真正写数据）才应该触发建表。executeQuery 是只读操作，不应该触发建表。

approach:
  从 executeQuery 中移除 _ensureTablesFromTemplate() 调用。这样：
  - 新开卡时，只有 applyEdits 或 executeMutation（真正写数据）才会触发建表
  - 加载历史聊天时，loadFromChat 已经通过 syncBridge.loadFromTableData 建好了表，executeQuery 不需要再建
  - executeQuery 在表不存在时，SQLite 会抛出 "no such table" 错误，这是合理的——调用方应该知道表还没建

  - 可维护性: 5/5 — 改动极小（删除一行），语义更清晰：只读操作不触发副作用

  - 可扩展性: 5/5 — 建表时机的控制更精确，未来如果需要更细粒度的控制也更容易
