# 清理楼层时冷表全量兜底快照

> **来源**：用户直接需求，无前置设计/审查文档。

## 1. 问题定义

### 1.1 当前行为

`purgeOldLayerData_ACU`（`src/service/chat/chat-service.ts:231`）在自动更新完成后执行，当 `含数据楼层数 > retainRecentLayers`（默认100）时：

1. 按消息索引收集所有含 `TavernDB_ACU_*` / `qrf_plot*` 字段的楼层
2. 从最旧的开始删除，直到只剩 `retainRecentLayers` 层
3. **整层删除**：`delete msg[key]`，不区分该消息内有哪些表

### 1.2 缺陷场景

| 场景 | 结果 |
|---|---|
| 表 A 频繁更新，数据分布在多个楼层 | 旧数据被清理，最新数据在保留楼层内 → 正常 |
| 表 B 在早期楼层写入一次后从未更新 | 其唯一数据落在被清理的旧楼层 → **表 B 完全消失** |

### 1.3 目标行为

清理前，扫描即将丢失的楼层数据。对于每张表，如果其数据**仅存在于被清理楼层中**（不在任何保留楼层中），则将该表的最新数据写入**边界保留楼层**（清理后最早保留的那层）作为兜底。

## 4. 实施设计

### 4.1 核心算法

在 `purgeOldLayerData_ACU` 中，**在删除循环之前**插入兜底快照步骤：

```
输入：indicesToPurge（将被删除的楼层索引数组）
      dataMessageIndices（所有含数据楼层索引数组）
      cutoffIndex（保留边界：dataMessageIndices[cutoffIndex] 及之后保留）

1. anchorIndex = dataMessageIndices[cutoffIndex]  // 边界保留楼层
2. retainedSet = new Set(dataMessageIndices.slice(cutoffIndex))  // 所有保留楼层的索引集合
3. orphanedData: Map<isolationKey, Map<sheetKey, Sheet_ACU>>  // 即将丢失的表数据

4. 按索引从小到大遍历 indicesToPurge：
   a. 解析 msg.TavernDB_ACU_IsolatedData
   b. 对每个 isolationKey，检查其 independentData 中每张表
   c. 如果该表在 retainedSet 的任何楼层中都不存在 → 记录到 orphanedData
      （后遍历的覆盖先遍历的，保证取最新版本）

5. 如果 orphanedData 非空：
   a. 读取 anchorIndex 消息的 IsolatedData
   b. 对每个 (isolationKey, sheetKey → data)：
      - 如果 anchor 消息中该 isolationKey 不存在 → 创建
      - 将 sheetKey 数据写入该 isolationKey 的 independentData
   c. 保存聊天
```

### 4.2 关键决策

| 决策 | 选择 | 原因 |
|---|---|---|
| 写入位置 | 边界保留楼层 `anchorIndex` | 确保清理后数据仍可被读取 |
| 覆盖策略 | 仅写入**不存在于任何保留楼层**的表 | 保留楼层已有该表数据时不需要兜底 |
| 遍历顺序 | 从旧到新遍历 `indicesToPurge` | 后遍历覆盖先遍历，取最新版本 |
| isolationKey | 按 isolationKey 分组处理 | 不同隔离标签下的表相互独立 |
| 旧版数据路径 | 同时检查 `TavernDB_ACU_IndependentData` 和 `TavernDB_ACU_Data/SummaryData` | 防止旧版路径数据丢失 |
| 保存时机 | 兜底写入后先 `saveChatToHost_ACU`，再执行原有删除循环 | 保证兜底数据在删除前已持久化，即使后续删除失败也不会丢失 |

### 4.3 风险点

| 风险 | 缓解措施 |
|---|---|
| 边界保留楼层可能不存在（极端情况） | `anchorIndex` 有效性检查，无效则跳过兜底 |
| 同一 isolationKey 下表数据冲突 | 后遍历覆盖（取最新），确定性行为 |
| 旧版数据路径与新版数据重复 | 先处理新版路径（`IsolatedData`），旧版路径仅作补充 |
| 兜底写入改变 modifiedKeys/updateGroupKeys 语义 | **不写入** modifiedKeys/updateGroupKeys；仅写入 independentData 主体 |
| 性能：大量表数据合并写入 | 正常场景下表数量有限（<50张），单次写入可接受 |

## 6. 验收标准

1. `purgeOldLayerData_ACU` 执行后，被清理楼层中的冷表数据出现在边界保留楼层
2. 已在保留楼层中有数据的表不会被重复兜底写入
3. 兜底写入不修改 `modifiedKeys` / `updateGroupKeys`（不干扰自动更新门禁）
4. 兜底写入失败时不应阻塞清理流程（catch 日志 + 继续）
5. 现有清理行为（chat[0] 保护、`retainRecentLayers` 阈值逻辑）不受影响
6. 日志清晰可追踪：哪些表被兜底、写入哪个楼层

## 7. 回滚策略

修改集中在单一函数 `purgeOldLayerData_ACU` 内部。回滚方式：

1. 移除兜底快照代码块，恢复原删除循环
2. 边界保留楼层中写入的兜底数据是**追加性**的——回滚代码后，已写入的兜底数据不会自动消失，但不影响功能（多一份冗余数据而已）
3. 如需清理已写入的兜底数据，用户可手动调用 `deleteLocalDataInChat_ACU` 或等待下一次清理周期自然移除
