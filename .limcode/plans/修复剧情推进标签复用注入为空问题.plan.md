# 修复剧情推进标签时序注入与复用为空问题实施计划

## 1. 计划来源与修订原因

来源：助手直接需求 + 后续补充语义。

助手补充的关键语义：

> 不用一致。例如这个标签是在第三个任务生成的，那第一、二、三任务引用占位符号时，应该用到的是上轮这个标签的内容，后边的四、五任务引用这个标签则应该是本轮生成的。

这句话会推翻上一版计划里“只修复同一个 Map 被多次读取后为空”的狭窄判断。上一版计划只能算勉强及格，甚至有点天真：它没有把“标签来源随任务顺序切换”作为核心需求建模。真正需求不是单纯 Map 读取不消费，而是**每个任务渲染时都要按当前执行进度解析标签来源**：

1. 本轮尚未产出目标标签：使用上一轮历史标签。
2. 本轮已有较早任务产出目标标签：后续任务使用本轮标签。
3. 同一标签可被多个后续任务重复读取，不得被第一个读取者消费。
4. 若某任务既引用又生成同名标签，该任务渲染 prompt 时仍只能使用执行前可见来源，不能预读自己的输出。

这不是小修小补，是运行时数据流语义修正。把它当作普通占位符替换 bug，会导致修完一个空值问题，又留下任务顺序错误这个更大的雷。

## 3. 目标行为定义

以任务按 runtime 顺序 `T1, T2, T3, T4, T5` 执行为例，上一轮历史中有 `<recall>旧内容</recall>`，`T3` 输出 `<recall>新内容</recall>`：

- `T1` prompt 中 `{{recall}}` 注入 `<recall>旧内容</recall>`。
- `T2` prompt 中 `{{recall}}` 注入 `<recall>旧内容</recall>`。
- `T3` prompt 中 `{{recall}}` 注入 `<recall>旧内容</recall>`；执行完成后将 `<recall>新内容</recall>` 合并进本轮标签状态。
- `T4` prompt 中 `{{recall}}` 注入 `<recall>新内容</recall>`。
- `T5` prompt 中 `{{recall}}` 注入 `<recall>新内容</recall>`。

如果本轮新标签为空或未提取成功，不应覆盖历史标签；后续任务继续使用历史标签。

如果本轮多个较早任务都产出同名标签，需明确合并策略：沿用现有聚合语义，将同名标签内容数组保留，并在注入时生成一个 `<tag>内容1\n\n内容2</tag>` 块。若产品希望“最新覆盖旧值”，那是另一个需求，不能偷偷改。

## 4. 影响范围与风险

### 4.1 当前 stage 并发模型与需求冲突

当前 `runPlotTasksRuntime_ACU` 对同 stage 使用 `Promise.all`。这意味着同一 stage 内 `T3`、`T4`、`T5` 如果并发，`T4/T5` 不可能读取 `T3` 的结果。助手的新语义明确要求“第三个任务生成后，第四/第五任务使用本轮内容”，这天然要求任务间存在顺序可见性。

所以有两条路：

- 方案 A：按全局 runtime 排序顺序串行执行所有任务。最稳，最符合需求，牺牲并发性能。
- 方案 B：保留 stage 概念，但同 stage 内也按 `order` 串行；stage 之间自然串行。兼容 UI 的 stage/order 语义，仍牺牲同 stage 并发。
- 方案 C：依赖感知执行，只并发没有标签依赖关系的任务。复杂度高，容易出错，不适合本次修复。

建议采用方案 B：保留 stage 分组用于日志、失败停止和排序，但每个 stage 内按 order 串行执行。否则需求和实现模型互相打架，继续硬修就是把 bug 换个地方藏起来。

### 4.2 标签读取缺失与大小写风险

当前多处直接 `Map.get(tagName)`，无法处理：

- 占位符大小写与提取标签配置不一致。
- relayMap 有本轮标签但某个占位符未命中时需要回退历史。
- 同一标签被多个任务重复读取时必须非破坏性。

需要统一读取函数，避免三处逻辑各写一套，之后再出三个不同版本的 bug。

### 4.3 extractInjectTags 语义风险

`extractInjectTags` 当前也写入 `extractedTags`，用于跨任务注入，但通过 `injectOnlyTagNames` 防止最终尾部追加。修复时必须保持：

- 可跨任务传递。
- 可覆盖历史来源。
- 不因大小写不一致导致最终尾部错误追加。

### Step 2：新增统一标签源解析工具

在 `src/service/runtime/plot-runtime/plot-tag-utils.ts` 增加内部或导出工具，建议：

- `getPlotTagMapValue_ACU(tagSourceMap, rawTagName)`
  - 精确匹配优先。
  - 精确失败后大小写不敏感匹配。
  - 返回 `{ found, value, actualTagName }`。
  - 不修改 Map，不消费数组。

- `mergePlotTagMaps_ACU(primaryMap, fallbackMap)` 或 `resolvePlotTagValue_ACU(currentMap, historyMap, tagName)`
  - 本轮 current 优先。
  - current 未找到才读 history。
  - 找到但内容为空数组/全空字符串时是否覆盖历史需谨慎：建议“无有效内容则视为未找到”，避免空输出覆盖历史。

这里不能偷懒直接 `new Map([...history, ...current])`，因为大小写匹配、空内容有效性和 actual key 记录都会被绕开。临时拼起来的合并 Map 看起来能跑，实际上就是事故温床。

### Step 3：改造占位符替换为“当前优先，历史回退”

调整 `replacePlotTagPlaceholders_ACU`：

- 接收单 Map 的兼容签名不破坏。
- 可扩展支持第二个 fallback Map，或接收 options：`{ fallbackTagMap }`。
- 替换 `{{tag}}` 时：
  1. 先从 current relayMap 找。
  2. 找不到或无有效内容，则从 historyMap 找。
  3. 都没有则保持旧行为输出空标签块或空字符串；为兼容当前测试，优先保持空标签块行为。

同步调整调用方：

- 第一批任务：currentMap 为空，historyMap 来自上一轮。
- T3 生成标签后，T4/T5 currentMap 中已有新标签，因此使用新内容。

### Step 4：改造任务级世界书触发文本

调整 `buildTaskWorldbookTriggerText_ACU`：

- 当前签名只支持 `plotContent` + 可选 `relayTagMap`，且有 relayMap 时不回退历史。
- 修改为支持 current + history fallback：
  - 从 prompt 中提取所有 `{{tag}}`。
  - 对每个 tag 按“本轮已完成标签优先，否则历史标签”取内容。
  - 构造触发文本。

这保证世界书触发依据与 prompt 实际注入内容一致。否则提示词里用的是新内容，世界书却按旧内容触发，系统会表现得像精神分裂——别笑，这种 bug 最难查。

### Step 5：改造 runPlotTasksRuntime_ACU 的执行与聚合时机

当前逻辑：

- stage 内 `Promise.all` 执行。
- stage 完成后才聚合所有成功结果。

目标逻辑：

1. 预先根据所有任务 prompt 中的占位符，从 `sharedContext.lastPlotContent` 构建历史标签 Map；或在每任务渲染前按需构建历史 Map。
2. 初始化 `currentRoundTags = new Map()`。
3. 按 `sortPlotTasksForRuntime_ACU(enabledTasks)` 或 `groupPlotTasksByStage_ACU` 后 stage/order 顺序执行。
4. 每个任务执行前传入：
   - `relayTagMap: currentRoundTags`
   - `historyTagMap` 或 `lastPlotContent` fallback
   - `useHistoryRelay` 不再作为互斥开关，而是表示是否允许历史 fallback。
5. 每个任务成功后，立即将其 `extractedTags` 合并进 `currentRoundTags`。
6. 后续任务看到新的 currentRoundTags。
7. 失败策略保持现有：某任务失败时停止后续任务并返回失败结果。若原逻辑是 stage 失败才停止，修订后需明确：串行执行中单任务失败即停止后续任务，等价于更早暴露失败。

建议保留 `successfulResults`，最终仍调用 `buildPlotSaveContentFromTaskResults_ACU(successfulResults)` 和 `buildFinalPlotInjectionMessage_ACU(...)`。

### Step 6：修正最终注入构造

`buildFinalPlotInjectionMessage_ACU` 应继续使用最终聚合的本轮标签，而不是历史 fallback。最终注入是对本轮剧情规划结果的交付，不应把未生成的历史标签混入最终结果，除非最终指令明确需要历史标签占位。这一点需要谨慎：

- 若最终指令 `{{recall}}` 期望本轮 recall，使用 current aggregatedTags。
- 如果本轮未生成 recall，而最终指令仍有 `{{recall}}`，当前行为会移除占位符并 fallback rawResponse。建议不引入历史 fallback，避免把上一轮内容伪装成本轮规划结果。

同时修复：

- 同一 `{{tag}}` 多次出现时每次完整注入。
- 大小写不一致时可命中。
- `injectOnlyTagNames` 判断大小写稳健，避免 injectOnly 标签被错误追加尾部。

## 6. 验收标准

- T1/T2/T3 在本轮标签生成前引用 `{{tag}}` 时使用上一轮标签。
- T3 生成同名标签后，T4/T5 引用 `{{tag}}` 时使用本轮标签。
- 同一标签可被多个后续任务重复读取，不会第一个任务读完后后续变空。
- 同一 prompt 内多个相同占位符都能注入完整内容。
- 世界书触发文本与实际 prompt 注入使用同一标签来源。
- `extractInjectTags` 仍支持跨任务传递，但不会污染最终尾部追加。
- 定向测试通过；typecheck 的既有 `baseUrl` 诊断单独记录。

## 8. 自我复查

这版计划比上一版靠谱，因为它终于把“标签来源随任务执行顺序切换”建进数据流了。不过仍有一个不漂亮的地方：为了满足 T3→T4 的即时传递，必须牺牲同 stage 并发或引入依赖调度。依赖调度太重，本次不建议碰；串行化更稳但会影响性能。这个代价必须在实现说明中写清楚，别偷偷改执行模型然后假装没有部署影响。
