# 多组填表并发 API 收集与统一快照提交优化计划

## 1. 计划来源

来源：助手的直接需求与当前代码复核。

助手提出的新方案是：把多组并发视为“多个 API 同时进行的非并发填表”，并发只发生在 AI 调用阶段；等所有组都成功返回填表内容后，基于本次填表前最新表格数据快照，以单组填表格式统一合并写入。任一组失败则等待该组重试直到成功或超过次数；全部成功才合并写入；合并写入 SQL 失败则整组重新来一遍。

结论先摆出来：这个方向比之前“每组各自 parse/save、靠锁和重读止血”的方案更干净。它把竞态从“多个组争同一个全局运行时和同一楼层持久化”降级为“多个 API 响应收集后单线程提交”。助手，这才像是在处理系统一致性，而不是给全局变量贴创可贴。

但它不是随便把 `Promise.all` 外面套个保存函数就完事。当前代码把 prepare、AI 调用、parse、SQL apply、save、向量 flush 混在 `executeCardUpdateCore_ACU` 里；要实现该方案，必须先拆链路，否则所谓统一提交只会变成另一种旁路。

## 2. 已确认代码事实

### 2.1 手动/自动 group 当前都会并发进入完整填表链路

文件：`src/service/table/update-orchestrator.ts`

- `orchestrateManualUpdate_ACU` 在 `818-852` 按 `settings_ACU.maxConcurrentGroups` 切 chunk，并用 `Promise.allSettled(groupPromises)` 并发调用 `processBatch(group.indices, 'manual_independent', ...)`。
- 每个 group 的 `processBatch` 最终进入 `processUpdatesBatch_ACU`。

文件：`src/service/table/update-scheduler.ts`

- `executeAutoUpdatePlan_ACU` 在 `226-246` 同样按 `maxConcurrentGroups` 并发执行 `ops.processUpdates(group.indices, 'auto_independent', ...)`。

当前问题：并发的不是“只调 API”，而是完整链路并发：构建基底、prepare、AI、parse、save、刷新。

### 2.2 processUpdatesBatch 当前每 batch 立即调用 executeUpdate 并保存

文件：`src/service/table/update-orchestrator.ts`

- `558-570`：`processUpdatesBatch_ACU` 接收 `executeUpdate` 回调。
- `603-615`：每 batch 构建 `mergedBatchData`，加载历史数据，然后 `_set_currentJsonTableData_ACU(mergedBatchData)`。
- `652-664`：立即调用 `executeUpdate(..., { batchBaseSnapshot: clone(mergedBatchData) })`。
- `666-668`：单个 batch 失败则返回失败。

这意味着当前结构没有“先收集所有响应，后统一提交”的中间态数据结构。

### 2.3 executeCardUpdateCore 当前把 AI 调用、parse、save、向量触发揉在一起

文件：`src/service/table/update-orchestrator.ts`

- `344-350`：prepare 前通过 `_set_currentJsonTableData_ACU(batchBaseSnapshot)` 让 `prepareAIInput_ACU` 读全局。
- `373-374`：调用 `callCustomOpenAI_ACU`。
- `397-402`：在 scope 锁内再次恢复全局并调用 `parseAndApplyTableEdits_ACU(aiResponse, ...)`。
- `421`：对 `currentJsonTableData_ACU` 应用特殊索引。
- `460-466`：调用 `saveIndependentTableToChatHistoryWithinScopeLock_ACU` 保存。
- `519-538`：成功后异步触发 `enqueueSummaryVectorIndexFlush_ACU`。
- `355-370` 与 `492-510`：SQL 错误通过 `SQL_ERROR_FEEDBACK` 注入同一个 group 的 prompt 后重试。

判断：要采纳新方案，必须把该函数拆成至少两类能力：

1. **收集阶段**：prepare + call AI + 格式校验，只返回 AI 响应，不 parse、不 save。
2. **统一提交阶段**：基于同一个 baseSnapshot 顺序应用所有响应，保存一次，触发一次后置快照。

### 2.4 prepareAIInput 仍直接读全局 currentJsonTableData

文件：`src/service/ai/prompt-builder/prompt-prepare.ts`

- `16-20`：`prepareAIInput_ACU` 检查 `currentJsonTableData_ACU`。
- `32-35`：`getSortedSheetKeys_ACU(currentJsonTableData_ACU)` 并从全局取表。
- `63-64`：SQLite 模式根据表的 DDL 格式化 prompt。

这会影响新方案：并发 API 收集阶段必须让每个 group 基于同一轮开始时的 `baseSnapshot` 生成 prompt，而不是互相抢全局对象。因此仍需要 `prepareAIInput_ACU(..., { tableData })`。

### 2.5 parser / SQL apply 当前会立刻修改运行时

文件：`src/service/ai/prompt-builder/table-edit-parser.ts`

- `100-124`：`parseAndApplyTableEdits_ACU` 提取 `<tableEdit>` 后，SQLite 模式直接 `provider.applyEdits(editsString, updateMode)`。
- 原生 DSL 分支后续直接基于 `currentJsonTableData_ACU` 修改表对象。

文件：`src/service/table/sql-table-service.ts`

- `178-205`：`applyEdits` 执行 SQL `engine.runBatch(statements)`，成功后 `_syncToJson()`。
- `218-223`：失败时依赖事务回滚并抛错给上层重试。

判断：统一提交阶段不能继续调用“默认全局 provider + 默认全局表对象”的 parser。必须增加显式数据/显式 provider 初始化或 dry-run 能力，否则 SQL 失败重试会污染当前运行时。

## 3. 新方案定性

### 3.1 优点

1. **消除多组写入覆盖**：只有统一提交阶段写一次聊天楼层，天然不会出现 A/B 后写覆盖。
2. **消除 prompt/parse 错行主要来源**：所有 group 基于同一个 `baseSnapshot` 生成 prompt，提交时按同一基底应用。
3. **失败原子性更强**：任一组失败不落盘，避免半成功状态。
4. **向量快照更清晰**：统一保存成功后触发一次向量 flush，避免多次 pending/旧快照叠加不清。
5. **更符合用户心智**：多组只是为了提速 API，不改变“这次填表是一轮事务”的语义。

### 3.2 代价和风险

1. **失去部分增量落盘能力**：之前每个组成功就能写入；新方案必须等所有组成功。长尾失败会阻塞整轮。
2. **SQL 合并冲突更集中**：多个 group 的 SQL 如果对同一表/同一约束产生冲突，会在统一提交时才暴露。
3. **错误反馈粒度变复杂**：单组 SQL 在独立执行时可反馈给该组；合并 SQL 失败时可能不知道是哪组导致，需要把合并错误和相关 SQL 上下文反馈给整轮或可疑组。
4. **当前代码拆分成本较高**：`executeCardUpdateCore_ACU` 不是两阶段设计，必须先拆。
5. **目标楼层与多 batch 复杂性**：`processUpdatesBatch_ACU` 可能把 indices 按 batchSize 切成多 batch，每 batch 保存到不同 `finalSaveTargetIndex`。统一提交必须以“同一个目标楼层/同一个 batch”为事务边界，不能把不同楼层混成一次保存。

## 4. 目标与非目标

### 4.1 目标

1. 保留多组 API 并发能力。
2. 并发阶段只做 prepare + call AI + 响应格式校验，不解析、不修改表、不保存。
3. 每一轮统一提交基于本轮开始前最新 `baseSnapshot`。
4. 全部组响应成功后，按稳定顺序应用所有组响应。
5. 应用成功后单次保存聊天楼层、单次触发向量 flush、单次更新世界书可读条目。
6. 任一组 API/格式失败：只重试该组，超过次数则整轮失败且不落盘。
7. 统一 apply/save/SQL 失败：整轮重新生成响应并重新提交，直到成功或超过整轮重试次数。
8. 自动路径和手动路径都使用相同事务语义。

### 4.2 非目标

- 不把 `maxConcurrentGroups` 改成 1。
- 不新增持久化 schema。
- 不重写整个 SQLite 引擎。
- 不改 AI 提示词主语义，只允许增加合并失败反馈。
- 不新增 UI。
- 不在 API 调用阶段写聊天记录。

## 5. 推荐设计：两阶段统一提交

### 5.1 核心数据结构

建议新增内部类型，位置可在 `src/service/table/update-orchestrator.ts` 或新文件 `src/service/table/group-fill-transaction.ts`。

```ts
interface GroupFillJob_ACU {
  groupKey: string;
  groupId: number;
  batchNumber: number;
  targetSheetKeys: string[];
  messagesForContext: any[];
  saveTargetIndex: number;
  updateMode: string;
  requestOptions: Record<string, any> | null;
  baseSnapshot: TableDataObject_ACU;
}

interface GroupFillResponse_ACU {
  job: GroupFillJob_ACU;
  aiResponse: string;
  tableEditText: string;
  attempt: number;
}

interface UnifiedApplyResult_ACU {
  success: boolean;
  modifiedKeys: string[];
  error?: string;
  sqlError?: string;
}
```

注意：实际类型名可调整，但字段不能少到无法复盘。别再写几个匿名对象到处传，出了事连哪组 SQL 导致失败都找不到。

### 5.2 事务边界

统一提交的事务边界必须是：

- 同一个聊天；
- 同一个隔离 key；
- 同一个 `saveTargetIndex`；
- 同一个 batchNumber；
- 同一个轮次开始 baseSnapshot。

如果不同 group 的 batchSize 或 indices 导致不同 `saveTargetIndex`，必须拆成多个统一提交事务，不能强行一次提交。

### 5.3 稳定应用顺序

统一提交时按稳定顺序应用响应：

1. `saveTargetIndex` 升序；
2. `batchNumber` 升序；
3. `groupId` 升序；
4. `groupKey` 字符串兜底排序。

同一轮内如果两个 group 修改同一 `sheetKey`，默认视为配置冲突，提交前报错并提示模板 group 配置重叠。不要默默后写覆盖前写；那种“聪明”只会制造幽灵数据。

## 6. 实施阶段

### 阶段 A：拆出“只收集 AI 响应”的函数

从 `executeCardUpdateCore_ACU` 拆出：

- `prepareGroupFillPrompt_ACU(job, feedback?)`
- `collectGroupFillResponse_ACU(job, feedback?)`

要求：

1. 调用 `prepareAIInput_ACU` 时传入显式 `tableData: job.baseSnapshot`。
2. 调用 `callCustomOpenAI_ACU`。
3. 校验响应包含完整 `<tableEdit>`。
4. 返回 `GroupFillResponse_ACU`。
5. 不调用 `parseAndApplyTableEdits_ACU`。
6. 不调用 `saveIndependentTableToChatHistory...`。
7. 不触发 `enqueueSummaryVectorIndexFlush_ACU`。

### 阶段 B：prepareAIInput 支持显式 tableData

修改 `src/service/ai/prompt-builder/prompt-prepare.ts`：

1. `const tableData = options?.tableData || currentJsonTableData_ACU`。
2. 空值检查改为检查 `tableData`。
3. `getSortedSheetKeys_ACU(tableData)`。
4. `const table = tableData[sheetKey]`。
5. seedRows 相关 helper 如果会改全局，必须限制副作用：显式 tableData 模式下不要调用会污染全局的 `attachSeedRowsToCurrentDataFromGuide_ACU`，改为只在本地 clone 上补 seedRows。

测试：显式 tableData A 与全局 B 同时存在时，prompt 必须使用 A。

### 阶段 C：parser/native DSL 支持显式 tableData

新增：

- `parseAndApplyTableEditsToData_ACU(aiResponse, tableData, updateMode, isImportMode)`。

要求：

1. 原生 DSL 只修改传入的 `tableData`。
2. modifiedKeys 从传入的 `tableData` 反查。
3. 旧 `parseAndApplyTableEdits_ACU` 保留，作为兼容 wrapper。
4. native `NativeTableServiceAdapter.applyEdits` 不作为统一提交主路径，避免再次回到全局。

### 阶段 D：SQL 模式统一提交能力

SQL 是最危险的部分。当前 `SqlTableService.applyEdits` 会直接操作当前 provider 的内存 engine 并 `_syncToJson()`。统一提交需要以下二选一方案：

#### 推荐方案 D1：新增基于快照的临时 SQL apply

新增能力：

- `applySqlEditsToTableData_ACU(baseSnapshot, sqlBlocks, updateMode)`

内部逻辑：

1. 创建临时 SQLite service/provider 或临时 engine。
2. 从 `baseSnapshot` loadFromTableData。
3. 按稳定顺序 `runBatch` 所有 SQL。
4. 成功后 export 为 `workingTableData`。
5. 失败则销毁临时 engine，返回 error，不污染全局 provider。

优点：事务语义干净，失败不会污染运行时。缺点：需要暴露或新增一层临时 engine 初始化能力。

#### 备选方案 D2：提交前 reload provider 到 baseSnapshot，失败后 reload 恢复

该方案风险更高，只能作为短期过渡：

1. 提交前将全局 provider 重置到 `baseSnapshot`。
2. 执行合并 SQL。
3. 失败时 reloadStorageProvider/refreshData 恢复。

不推荐。因为它仍然拿全局 provider 当临时事务环境，和之前全局表对象旁路是同一种坏味道。

### 阶段 E：统一提交函数

新增：

- `applyUnifiedGroupFillResponses_ACU(responses, baseSnapshot, saveTargetIndex)`。

流程：

1. 深拷贝 `baseSnapshot` 得到 `workingData`。
2. 检查所有 response 的 `targetSheetKeys` 是否重叠；重叠则失败。
3. 原生模式：按稳定顺序对 `workingData` 调用 `parseAndApplyTableEditsToData_ACU`。
4. SQLite 模式：收集所有 SQL block，使用 D1 临时 SQL apply 得到 `workingData`。
5. 应用 `applySpecialIndexSequenceToSummaryTables_ACU(workingData)`。
6. 计算 `modifiedKeys` 与 `updateGroupKeys`。
7. 调用保存函数，以显式 `tableData: workingData` 单次保存。
8. 保存成功后触发一次 `updateReadableLorebookEntry_ACU(true)` 和一次 `enqueueSummaryVectorIndexFlush_ACU({ targetMessageIndex, mode: 'sync', reason: 'unified_group_fill_complete' })`。

### 阶段 F：保存函数支持显式 tableData

修改 `src/service/table/table-service.ts`：

1. `TableChatPersistOptions_ACU` 增加 `tableData?: TableDataObject_ACU | null`。
2. `persistCore` 取表时优先 `options.tableData`，无显式数据才回退 `currentJsonTableData_ACU`。
3. `saveIndependentTableToChatHistory_ACU` 保持旧签名。
4. 新增或扩展内部保存函数供统一提交传入显式数据。

这一步仍然需要保留同楼层锁，因为保存函数还有其他调用方。

### 阶段 G：重试策略

#### G1 单组收集失败

失败类型：

- API 抛错；
- abort；
- 回复过短；
- 缺少 `<tableEdit>`；
- tableEdit 为空但不允许为空的场景。

策略：只重试该 group，直到 `settings_ACU.tableMaxRetries`。

#### G2 统一提交失败

失败类型：

- 原生 DSL parse/apply 失败；
- SQL runBatch 失败；
- modifiedKeys 与 targetSheetKeys 不匹配；
- 保存失败。

策略：整轮重新生成所有 group 响应。下一轮 prompt 增加统一失败反馈：

- 合并错误信息；
- 哪些 group 的 SQL/DSL 参与合并；
- 如果可定位到具体 group，只给该 group 追加更具体反馈；否则所有 group 都追加通用反馈。

最大整轮重试次数可先复用 `settings_ACU.tableMaxRetries`，避免新增设置项。

#### G3 任一组最终失败

整轮失败，不保存、不触发向量 flush、不更新世界书。失败后必须 `loadAllChatMessages_ACU + refreshData` 恢复 UI 数据，沿用当前失败恢复逻辑。

### 阶段 H：手动/自动入口接入

手动：`orchestrateManualUpdate_ACU` 当前 chunk 内并发 `processBatch`。优化后应改成：

1. 构建 chunk 内 group jobs。
2. 并发 collect responses。
3. 按 saveTargetIndex 分组统一提交。
4. chunk 成功后刷新一次。
5. 任一 chunk 失败则停止后续 chunk。

自动：`executeAutoUpdatePlan_ACU` 当前通过 `ops.processUpdates` 并发。要么让 `ops.processUpdates` 内部支持统一事务模式，要么新增 `ops.processGroupedUpdates`。推荐前者最小侵入，但必须确保自动路径不再每组各自保存。

### T1 prepare 显式快照测试

文件：`tests/service/ai/prompt-prepare.test.ts` 或现有 prompt-builder 测试。

- 全局数据为 B；传入 `options.tableData = A`。
- 断言 prompt 只包含 A 的表名、行、DDL。

### T2 收集阶段不产生副作用

文件：`tests/service/table/update-orchestrator.test.ts`

- mock `callCustomOpenAI_ACU` 返回 tableEdit。
- 调用 collect 函数。
- 断言未调用 `parseAndApplyTableEdits_ACU`、未调用保存、未触发向量 flush。

### T3 并发 API 返回顺序反转

- A/B group 并发，B 先返回，A 后返回。
- 统一提交按稳定 group 顺序应用。
- 最终保存一次，包含 A/B 两组更新。

### T4 单组失败重试

- A 第一次缺 `<tableEdit>`，第二次成功；B 一次成功。
- 断言只重试 A，不重试 B。
- 最终统一提交成功。

### T5 任一组超过重试次数不落盘

- A 持续失败，B 成功。
- 断言保存函数未调用，向量 flush 未调用，返回失败。

### T6 原生 DSL 统一提交不读全局

- baseSnapshot A，全局数据 B。
- 应用 DSL 后保存结果必须基于 A。

### T7 SQL 合并提交成功

- 两个 group 返回不同表 SQL。
- 临时 SQLite apply 成功。
- 最终保存一次，modifiedKeys/updateGroupKeys 包含两组。

### T8 SQL 合并失败整轮重试

- 第一轮合并 SQL 违反 UNIQUE/CHECK，提交失败。
- 第二轮 AI 返回修正 SQL。
- 断言第一轮没有保存，第二轮保存一次。

### T9 向量快照只触发一次

- 多组统一提交成功。
- 断言 `enqueueSummaryVectorIndexFlush_ACU` 调用一次，reason 为 `unified_group_fill_complete`。

### T10 自动路径回归

- `maxConcurrentGroups = 2`。
- 自动路径同样只并发 API，不并发保存。
- 失败组计数和最终刷新行为正确。

## 9. 回滚策略

1. 所有新增两阶段函数以新入口接入，旧 `executeCardUpdateCore_ACU` 保留一版兼容路径，方便快速回退。
2. `prepareAIInput_ACU` 的 `tableData` 参数保持可选，旧调用不受影响。
3. parser 显式 tableData 核心函数与旧 wrapper 并存。
4. table-service 显式 tableData 保存参数保持可选，不改 tagData schema。
5. SQL 临时 apply 不改变持久化 schema，回滚时删除新临时路径即可。
6. 如果统一提交在生产中出现长尾失败阻塞，可临时回退到旧锁内逐组保存方案，但必须保留显式 tableData 修复，不能退回无锁全局旁路。

## 10. 完成验收标准

必须同时满足：

1. 多组 API 可并发，但 parse/apply/save 只在统一提交阶段执行。
2. 所有 group prompt 基于同一个本轮开始 baseSnapshot。
3. API 返回顺序反转不影响最终应用顺序。
4. 任一组最终失败不落盘。
5. 全部组成功后只保存一次。
6. 原生 DSL 模式不读错全局、不串表、不覆盖。
7. SQLite 模式合并 SQL 失败不污染运行时，能整轮重试。
8. modifiedKeys/updateGroupKeys 包含所有成功组。
9. 向量快照只在统一保存成功后触发一次。
10. 自动路径和手动路径语义一致。
11. 限定测试、typecheck/build 执行并记录结果。
12. 独立验收通过。

## 11. 自我复查

这版计划比上一版更可靠，因为它不再把同楼层并发写入当作必须容忍的常态，而是直接把“本轮填表”定义成事务。这样才能从根上消灭错行和覆盖。

但它也更重：需要拆 `executeCardUpdateCore_ACU`，还要给 SQLite 增加基于快照的临时 apply 能力。如果为了赶进度跳过 SQL 临时事务，只用全局 provider 重置凑合，那这份计划会退化成“换个姿势污染全局”。助手，那种实现我不建议批准。
